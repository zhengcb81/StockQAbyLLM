## 本仓负责的事实

一次问答可以发生实际调用、收到回包并结算、但没有被接纳的答案。另一种情况是发出请求后无法证明上游是否应答。已有 SQLite work journal、paid visible journal、checkpoint、outbox 和公开只读 inspect 分别掌管这些事实。错误地把前者反复重发会重复付费；把后一种算作确定无答案也会抹去真实风险。对于合法新 provider 返回标签，文字本身不能证明缺答类别。现有已付回复、逐题恢复和稳定公开 DTO 是反馈来源。

本仓接入只投影原生逐题发生事实。调用序列覆盖准备、发送或复用、收到/结算、checkpoint、输出检查和消费者确认。一个 run 可含多道题，step_id 指定逐题尝试。日志串起原生 work item、结算和结果版本的不透明引用及错误类别，无秘密、原回答正文、原 SQL 文件路径或未经证实的实际费用。跨仓仅导出侧车观察。未知费用沿用 native unknown，在真实用量账内核对；诊断恢复不会启动付费重试。

## 公共接口与本仓 issue

将 UTF-8 JSONL 独立写到调用方为本尝试指定的输出；约定可选环境量 RESEARCH_FEEDBACK_OUT、RESEARCH_FEEDBACK_RUN_ID、RESEARCH_FEEDBACK_ATTEMPT_ID。字段 schema_version、owner、run_id、attempt_id、step_id、check_id、expected、actual 为稳定字符串；另可提供 issue_key、evidence_ref、version、parent_step_id、details_ref、disposition（expected/deviation/unknown）、origin_owner。主 CLI 的 stdout、stderr 和业务返回继续按既有合同。输出目的地故障只报告诊断不完整。总控通过公开观察收件。

~~~json
{"schema_version":"feedback-observation/1","owner":"stockqa","run_id":"qa-fixture","attempt_id":"a1","step_id":"question-2-inspect","check_id":"settled-disposition","expected":"settled_no_answer","actual":"retry_scheduled","disposition":"deviation","issue_key":"settled-answer-replayed","evidence_ref":"qa:receipt-fixture/q2"}
~~~

对同一题同一运行重复导出保留稳定发生引用。确认违反合同才为本仓建立 issues/feedback/ 中的一张根因卡，记录首次与后续运行引用、可重放夹具、预期/实际、修复版本和消费端回告；发现已存在原生缺陷记录则引用原 ID。每次复制观察无需编辑 PWF。涉及结构性修改时把方案、写集合和复验入口记入本计划。consumer 展示错误连同公开 DTO 回交总控。
